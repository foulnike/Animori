# Списки, хранение и сохранность

Где хранятся пользовательские данные, как они не теряются и как уезжают наружу.

## Список односторонний

Правки остаются на устройстве и на сервер не уезжают никогда. AniList — источник переноса, а не хранилище. Очереди правок и отправщика в коде нет.

Перенос по умолчанию сливает, а не замещает. Источников переноса три — AniList по входу, Шикимори по нику, файл выгрузки MyAnimeList.

Наружу список уходит тремя способами, каждый по действию человека: выгрузкой в XML, копией в облако и дублем снимка в файл на этой же машине.

Пользовательские данные — закладки (статус, оценка, число серий, пересмотры, даты, заметки), скрытые рекомендации, настройки. Первое невосполнимо.

## Настройки

`core/settings.ts`. Читать `settings.x` в момент использования, а не копировать при загрузке. До `await loadSettings()` в модуле лежат дефолты, а импорты выполняются до `start()` в `app/main.ts`.

Логировать из модуля можно: журнал настроек не читает, иначе был бы цикл.

## Хранилище моста

`Bridge.storage`. Хранилище моста про транзакции не знает, поэтому записи выстраиваются цепочкой — `core/store-chain.ts`: идущая запись держит следующую за собой. Порядок один на всех писателей.

## Снимок

`core/snapshot.ts` — то из данных пользователя, что потерять нельзя. Склад ответов сети (`db.ts`) в него не входит.

Базы приложения нет: источник правды — массив в памяти, на диске одна запись. Плюс дубль файлом через `files.rs`. Имя файла — только из списка в `files.rs`, каталог только приватный.

Версия снимка — шестая. Миграций схемы нет: чужая версия читается с нуля, список восстанавливается одним запросом к серверу. Номер MAL добавлен без поднятия версии — поле необязательное.

В снимке лежат латинские и английские названия, но не русские: русское зависит от настроек источников и хранится на складе. Картинок в снимке нет.

### Перенос с сервера

`refreshFromServer(mode)` в `core/collection.ts` зовётся только по действию человека.

| Способ | Что делает |
| :--- | :--- |
| `merge` | сливает ответ сервера с памятью по времени правки |
| `replace` | вычищает память и кладёт ответ сервера |

Правила слияния: при равных метках побеждает сервер; при победе нашей записи пустоты дополняются (номер MAL и латинские имена); записи, которых в ответе нет, остаются. Смена счёта переводит перенос в `replace`.

`unlinkCollection` оставляет записи и убирает связь с сайтом. `forgetCollection` удаляет местный список, только по прямой просьбе.

## Журнал активности

Отдельная запись `AM_ACTIVITY` в `core/activity.ts`, мимо снимка: `updatedAt` — одно поле на тайтл, оно перезаписывается при каждой правке. Журнал append-only, потолок 6000 событий. Пишет его одна точка — `editEntry` в `core/collection.ts`; вид правки выбирает `activityOfEdit`, даты начала и конца в журнал не пишутся. Плеер не пишет ничего: место остановки и история просмотра хранятся под своим ключом (`screens/player-keep.ts`). Старые дни из снимка не восстанавливаются — сетка показывает только то, что человек отметил сам.

## Дубль в файле

`src-tauri/src/files.rs` читает и пишет файлы в закрытом каталоге программы: белый список имён, запись через временный файл с переименованием, потолок 8 МБ, наружу возвращается имя, а не путь.

| Имя | Что это |
| :--- | :--- |
| `animori-snapshot.json` | дубль снимка |
| `animori-dataset.json` | датасет названий, около четырёх мегабайт |

Дубль снимка пишется на уходе в фон, при закрытии окна (`visibilitychange` и `pagehide`, не `beforeunload`: в WebView он часто не приходит) и при переносе списка. Читается, только когда в хранилище пусто или бито, и сразу возвращается в хранилище.

## Выгрузка в XML

Формат — экспорт MyAnimeList: принимают Шикимори, AniList, Kitsu и MAL. Сборка строки — `core/mal-xml.ts`, без сети и моста: на входе записи, на выходе строка. Записи без номера MAL возвращаются поимённо. Сохранение — `app/save-file.ts` через системный выбор файла (мост `AnimoriFiles`); команды `animori_export_*` интерфейс не вызывает.

## Источники данных

| Источник | Что даёт |
| --- | --- |
| AniList (GraphQL) | каталог, список пользователя, тайтлы, люди, расписание |
| Шикимори (REST + GraphQL) | русские имена, описания, хронология, журнал, поиск по-русски |
| Kodik, Aniliberty | видео |
| Яндекс Диск | облачная копия списка |
| `animori-data` | датасет русских названий и карта MAL ↔ AniList |

## Датасет названий

Файлы выпуска на диске, читаются без сети: `core/dataset-names.ts` между памятью и складом.

Датасет собирается в отдельном репозитории `foulnike/animori-data` и выходит раз в неделю. Клиент тянет его сам:

1. при старте `updateDatasetNamesInBackground()` спрашивает опись `index.json` по постоянному адресу `releases/latest/download`, с `If-None-Match`;
2. `304` означает «тот же выпуск» — тела нет, сравнивать нечего;
3. если выпуск новее, качаются оба файла, сверяются по `sha256` и заменяют слепок целиком;
4. новый выпуск начинает работать со следующего запуска: в память текущего он не попадает.

Между проверками — `LIFE_DATASET_CHECK` (12 часов). Разброс считается от даты установленной сборки. Неудача час проверки не сдвигает. Зеркала у клиента нет.

Порядок чтения имени четырёхуровневый: память запуска, датасет, склад IndexedDB, сеть. Датасет выше склада: он свежее и полнее. Вставка сделана в `core/media-title.ts`.

В `settings.ts` источник названий один — Шикимори. Датасет строится по нему же: только у Шикимори каталог перечисляется страницами и только он отдаёт кириллицу тем же ответом. Второго источника в рантайме нет.

## Облако

Яндекс Диск. Копия лежит в папке приложения (`app:`, область `disk.app_folder`): корня Диска пропуск не видит. Пропуск вводится руками в `CloudBox.vue` и хранится в `am_cloud_token`; копию также читают по опубликованной ссылке (`linkInfo`/`pullByLink`), и та пропуска не требует.

Облако читает только по действию человека. Формат копии — `core/cloud-file.ts`, модуль чистый: список покидает машину только здесь. Провайдер один.

Файл настроек `animori-settings.json`: пропуск облака (`am_cloud_token`) шифруется через DPAPI (`secrets.rs`), а `auth_token` и `set_proxy_pass` лежат открытым текстом. `CLOSED_KEYS` (`storage.rs`) запрещает читать `auth_token` только из окна через `animori_storage_read` — это не шифрование.
